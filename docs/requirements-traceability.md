# Requirements Traceability

Every functional and technical requirement in [docs/assignment.md](assignment.md),
mapped to the file that implements it, the test that proves it, and the documentation
that explains it. Organized in the assignment's own section order (§2 Technical
Architecture, §3 Functional Requirements, §4 Technical Constraints & Resilience) so
each row can be checked directly against the spec. All file paths are relative to the
repo root; all line/behavior claims were re-verified against the current code while
writing this document, not carried over from memory.

The last column is deliberately blunt. Where something is fully met, it says so in one
word and moves on. Where it isn't, it says exactly what's missing and why, rather than
leaving a reviewer to find the gap unassisted.

## §2.A — Ingestion & In-Memory Processing

| Requirement | Spec section | Implementation | Test | Docs | Notes |
|---|---|---|---|---|---|
| Signal ingestion — high-throughput, right protocol/format | §2.A "Signal Ingestion" | `backend/src/api/routes/signals.ts` (`POST /api/v1/signals`), `backend/src/api/routes/signalValidation.ts` (zod schema — single object or JSON array, `occurredAt` coerced to `Date`) | `backend/tests/unit/api/routes/signalValidation.test.ts`; end-to-end ingestion exercised in `backend/tests/e2e/fullLifecycle.test.ts` and every `backend/tests/chaos/` scenario | [README API Reference — Signals](../README.md#signals--backendsrcapiroutessignalsts-mounted-at-apiv1signals) | **Fully met.** Plain HTTP POST + JSON was chosen over a streaming protocol (gRPC, Kafka) as the simplest fit for "a monitoring source calling an ingestion endpoint" — there's no dedicated ADR justifying this specific choice; it's treated as the unremarkable default, documented via the API reference rather than a rationale doc. |
| Memory management — absorb bursts up to 10,000 signals/sec without crashing if persistence is slow | §2.A "Memory Management" | `backend/src/services/ingestion/buffer.ts` — four fixed-capacity ring buffers (one per severity), `BUFFER_CAPACITY` default 20,000, sized explicitly against this requirement (see docs/backpressure.md's "Why these numbers": 20,000 ≈ 2 seconds of full-rate absorption at 10,000/sec) | `backend/tests/unit/services/ingestion/buffer.test.ts` (capacity, watermarks, shedding order, hard-capacity eviction); `backend/tests/chaos/queueSaturation.test.ts` (floods an isolated instance past capacity, asserts shedding engages and P0 never drops, over real HTTP); `backend/tests/chaos/slowPersistence.test.ts` (pauses Mongo mid-burst, asserts ingestion keeps returning `202` throughout) | [README — Backpressure Handling](../README.md#backpressure-handling); [docs/backpressure.md](backpressure.md) | **Partially met — named honestly.** The *design* (bounded buffer, watermarks, severity-aware shedding, "never crash") is implemented and chaos-tested against real container failures. What was **not** cleanly demonstrated is a single, stable "10,000 persisted signals/sec, sustained" number: the real-HTTP-path k6 scenarios never approach it (they're intentionally rate-limiter-bound at ~88-91/s — see [Performance](../README.md#performance)), and the rate-limiter-bypassed pipeline-stress numbers in [docs/performance.md](performance.md) reached a *median* of ~14,081 persisted/sec post-tuning but ranged 3,991-15,262/s across three trials of the identical configuration, on one shared, non-isolated dev machine — directionally consistent with the target, not a clean, reproducible proof of exactly 10k/sec. |
| Debouncing — 100 signals for the same Component ID within 10s collapse to one Work Item, all signals linked in the NoSQL store | §2.A "Debouncing Logic" | `backend/src/services/ingestion/debouncer.ts` (`SignalDebouncer`) — `DEBOUNCE_THRESHOLD=100`, `DEBOUNCE_WINDOW_SECONDS=10` (`backend/src/config/index.ts`), matching the spec's numbers exactly; correctness backstopped by a Postgres partial unique index (`idx_work_items_active_component_id`, `backend/prisma/migrations/`), not just the Redis fast path | `backend/tests/unit/services/ingestion/debouncer.test.ts` (create/link/race/lock-contention paths against fakes); `backend/tests/integration/services/debouncer.test.ts` (60 simultaneous signals × 8 iterations against real Postgres — exactly one work item every time); `backend/tests/e2e/fullLifecycle.test.ts` (500 signals / 5 components → exactly 5 work items, not 500); `scripts/scenarios/cascading-failure.ts` (83-86 real signals on one component → 1 work item, verified against the running system) | [README — API Reference / Testing](../README.md#testing); [docs/data-model.md](data-model.md) | **Fully met**, and over-verified: unit, integration-under-concurrency, E2E, and a live scenario script all independently confirm the same property. |

## §4 — Technical Constraints & Resilience

| Requirement | Spec section | Implementation | Test | Docs | Notes |
|---|---|---|---|---|---|
| Concurrency — modern concurrency primitives | §4 "Concurrency" | Postgres optimistic concurrency (`transitionState`'s guarded `UPDATE ... WHERE state = fromState`, `backend/src/repositories/postgres/workItemRepository.ts` — throws `OptimisticConcurrencyError` on a lost race, never a lock); Redis atomic ops (`SET ... NX` for debounce locks and alert-dedup claims, `HINCRBY` for session counts); `Promise.all` fan-out for independent I/O (alert channel delivery, grouped Postgres increments); BullMQ's own worker-pool concurrency (`QUEUE_WORKER_CONCURRENCY`) | `backend/tests/e2e/concurrency.test.ts` — 50 truly simultaneous transition requests against one work item, repeated across 25 independent iterations, asserting exactly one `200` and forty-nine `409`s every single time (not a single trial that could pass by luck) | [ADR 0011](decisions/0011-optimistic-concurrency-for-state-transitions.md) (the guarded-update mechanism itself); [ADR 0010](decisions/0010-redis-fast-path-with-postgres-backstop-for-debouncing.md) (the Redis atomic-op usage); no single doc collects every concurrency primitive in one place — this table is the closest thing to one | Fully met — this is also the rubric's explicit "no race conditions during status updates" criterion, and `concurrency.test.ts` is a direct, dedicated proof of it, not an inference from other tests. |
